# 设计说明

## 1. 设计目标

项目目标是实现一个能够看懂、能够本地和局域网演示的一对一聊天室。重点不是高并发，而是把下面几件事解释清楚：

- 浏览器如何找到在线用户。
- 两个用户如何建立并显示同一段会话。
- FastAPI 如何接收、保存并返回消息。
- 为什么刷新页面后消息仍然存在。
- 如何在同一个局域网中让手机和电脑互相通信。

## 2. 总体结构

```text
浏览器 A                FastAPI 服务                浏览器 B
   |                        |                          |
   |-- 登录和心跳 --------->|                          |
   |<-- 在线用户与最近会话 --|                          |
   |                        |<--------- 登录和心跳 ----|
   |-- 发送消息 ----------->|                          |
   |                        |-- 保存到内存和 JSON -----|
   |                        |                          |
   |<-- 轮询当前会话消息 ----|                          |
   |                        |<--------- 轮询消息 ------|
```

后端同时提供：

- `/` 和 `/static/*`：网页、样式和 JavaScript。
- `/api/*`：聊天业务接口。

因为前后端同源，不需要额外配置 CORS，也不需要在 JavaScript 中写死服务器地址。

## 3. 为什么使用 HTTP 轮询

本项目选择短轮询而不是 WebSocket，原因是实现直观，方便初学者逐步调试。

- 心跳请求每 2 秒执行一次，用来更新在线状态。
- 当前会话的消息请求每 1 秒执行一次。
- 拖动窗口、网络断开或手机进入后台时，页面恢复后立即补发心跳和消息请求。

它的缺点是实时性不如 WebSocket，并且会产生更多 HTTP 请求。对于几台到十几台设备的课堂演示，这种方式足够简单清楚。

## 4. 用户身份

用户第一次输入昵称时，服务端生成 UUID。前端把用户 ID 和昵称保存到当前标签页的 `sessionStorage`。

刷新页面时：

1. 页面从 `sessionStorage` 取回用户 ID 和昵称。
2. 再次调用 `POST /api/session`。
3. 服务端识别同一个用户 ID，更新昵称和最后心跳时间。
4. 前端继续读取该用户的历史会话。

这不是正式登录。由于没有密码或令牌，调用者可以伪造用户 ID，因此只能用于可信局域网和教学演示。

## 5. JSON 数据结构

`data/chat_data.json` 的示例：

```json
{
  "next_message_id": 3,
  "users": {
    "用户 UUID": {
      "id": "用户 UUID",
      "nickname": "小明",
      "created_at": "2026-10-07T08:00:00+00:00",
      "last_seen": "2026-10-07T08:05:00+00:00"
    }
  },
  "messages": [
    {
      "id": 1,
      "sender_id": "用户 UUID",
      "receiver_id": "另一个用户 UUID",
      "content": "你好",
      "created_at": "2026-10-07T08:01:00+00:00"
    }
  ]
}
```

`users` 使用字典保存用户，按 ID 查询速度快。`messages` 使用数组保存，便于按时间顺序遍历和展示。

## 6. 在线状态

服务端不保存永久的 `is_online` 字段，而是根据 `last_seen` 动态计算：

```text
当前时间 - 最后心跳时间 <= 6 秒
```

满足条件时用户在线。这样即使浏览器异常关闭，没有发送“退出”请求，用户也会在 6 秒后自动变成离线。

在线列表会排除当前用户本人。

## 7. 最近会话

项目没有单独创建 `conversations` 表。对话关系由消息本身推导：

1. 遍历当前用户参与的所有消息。
2. 根据另一方的用户 ID 分组。
3. 每组只保留消息 ID 最大，也就是时间最新的一条。
4. 按最后一条消息 ID 倒序排列。

只要发过消息，即使对方后来离线，用户仍然能在“最近会话”中打开历史。

## 8. 消息发送规则

发送一条新消息时，服务端依次检查：

1. 消息内容是否通过 Pydantic 校验。
2. 发送者是否存在。
3. 接收者是否存在。
4. 接收者是否在 6 秒在线时间内。
5. 接收者不是发送者本人。

任何检查失败都不会写入消息。接收者离线时返回 HTTP 409，前端将发送框禁用并显示原因。

历史查询不要求对方在线，所以离线用户仍可追溯，但不能继续产生新消息。

## 9. 并发与持久化

FastAPI 的异步接口可能同时收到多个请求。为了避免两个请求同时修改同一份数据，`storage.py` 使用 `asyncio.Lock` 包住每次读改写操作。

保存时不会直接覆盖原文件，而是：

1. 把新数据写到 `chat_data.json.tmp`。
2. 调用 `flush()` 和 `os.fsync()` 确保内容写入磁盘。
3. 使用 `os.replace()` 原子替换正式文件。

这样即使替换前程序异常退出，原文件仍然完整。该方案适合单进程运行，不应使用多个 Uvicorn worker。

## 10. 关键函数

| 文件和函数 | 作用 |
| --- | --- |
| `main.create_session` | 创建或恢复用户，返回在线列表和最近会话 |
| `main.heartbeat` | 更新在线时间，并刷新前端侧栏 |
| `main.send_message` | 校验并保存在线用户之间的消息 |
| `main.get_messages` | 返回完整历史或增量消息 |
| `storage.ChatStore.initialize` | 启动时读取或创建 JSON |
| `storage.ChatStore.add_message` | 在线校验、生成消息 ID、持久化 |
| `storage.ChatStore.list_recent_conversations` | 从消息中计算每个聊天对象的最后一条消息 |
| `storage.ChatStore._write_data_to_disk` | 临时文件加原子替换 |
| `app.js.runHeartbeat` | 前端心跳和断线重试 |
| `app.js.pollMessages` | 完整历史和增量消息轮询 |
| `app.js.appendMessages` | 去重、创建消息元素并滚动到底部 |

## 11. API 一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/session` | 登录或刷新后恢复用户 |
| POST | `/api/heartbeat` | 更新在线状态 |
| GET | `/api/messages` | 获取历史或增量消息 |
| POST | `/api/messages` | 发送消息 |
| GET | `/api/health` | 健康检查 |

## 12. 局域网原理

默认启动命令使用：

```text
host = 0.0.0.0
port = 8000
```

`0.0.0.0` 表示监听所有本机网卡。其他设备访问：

```text
http://服务电脑的局域网IPv4地址:8000
```

浏览器先下载同一个前端页面，再由页面中的相对路径调用同一台服务器上的 API，因此所有设备看到的是同一份用户和消息数据。

常见失败原因：

- 服务只监听 `127.0.0.1`。
- Windows 防火墙阻止入站连接。
- 两台设备不在同一局域网。
- 使用了 VPN 地址而不是 Wi-Fi 地址。
- 路由器启用了客户端隔离。
- 校园网禁止局域网设备互访。

## 13. 前端结构

页面分为两个状态：

- 登录状态：输入昵称。
- 聊天状态：左侧显示当前用户、在线用户和最近会话，右侧显示当前对话。

手机屏幕下，侧栏和聊天区改成两个全屏页面。点击聊天对象进入会话，点击“返回”回到用户列表。

用户输入全部通过 `textContent` 写入页面，不直接拼接 HTML，因此昵称和消息中的标签不会作为 HTML 执行。

## 14. 已知限制

- 无真实登录、权限验证和加密。
- 只支持一对一聊天。
- 只允许在线发送，不支持对离线用户留言。
- JSON 不适合大量消息和高并发。
- 不支持多 worker、多进程或多服务器共享。
- 在线状态和消息都有轮询间隔带来的延迟。
- 不支持公网、跨网段、NAT 穿透和复杂网络环境。
